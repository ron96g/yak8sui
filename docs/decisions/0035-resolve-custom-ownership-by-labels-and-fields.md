# Resolve custom ownership by composite labels and field references

Allow each configured parent/child type pair to select exactly one ownership resolver: `ownerReferences`, `labelJoin`, or `fieldReference`. Both endpoint types remain explicitly observed, and every candidate remains independently current and authorized; a resolver proves an edge but never grants access.

A `labelJoin` rule declares one or more parent-label/child-label key pairs. Every pair must be present and equal. It models logical ownership, so deleting a parent and creating another parent with the same joined labels intentionally rebinds the edge to the replacement parent's actual metadata and UID. A `fieldReference` rule declares one path under the child's spec or status containing one Kubernetes ObjectReference-shaped value: API version, kind, name, UID, and namespace where scope requires it. Field references are UID-stable and arrays are not supported.

Custom resolvers require at most one matching parent for each child. No match means no edge; multiple matches are not resolved by ordering and instead make the affected branch incomplete with a safe diagnostic. Existing owner-reference resolution retains its multiple-parent behavior. All resolvers enforce valid Kubernetes namespace/cluster scope combinations, preserve lazy bidirectional traversal, and feed the existing neighborhood HTTP/SSE contract. Configuration is restart-required, rejects resolver-specific fields that do not belong to the selected resolver, and permits only one rule for a directional parent/child type pair.
